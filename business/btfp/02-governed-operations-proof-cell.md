# Governed Operations Proof Cell — Outline

*The concrete next step after the diagnostic. One narrow operational path, run so that the record, the workflow, the report, and the audit trail all tell the same truth. This is where the diagnostic (Ratatosk) meets governed execution (ROPE) — and where a prospect sees value without an ERP-replacement conversation.*

---

## The promise

> Instead of replacing your ERP, we take **one operational path**, establish what its terms actually mean, and run it so that state changes are governed, policy is enforced before the record changes, and the audit trail is generated by the operating path itself — not reconstructed afterward. We prove the slice, on your data, in weeks.

The point is not the software. The point is that at the end, **four things that disagree today tell the same story**: the system record, the spreadsheet/side-process, the report leadership reads, and the evidence an auditor would ask for.

## Choosing the path (candidates)

Pick one narrow, high-legibility path with (a) a clear state change, (b) a real policy/authority attached, and (c) an audit or reconciliation pain. Recommended, in order:

1. **Purchase-order approval & issuance governed by spend authority** *(default recommendation).* Legible to every manufacturer: a PO above a threshold must have the correct approval authority before it can be issued; segregation of duties enforced; every decision audit-ready. Pain: spend controls that live in email/Excel, audit findings, "who approved this?"
2. **Quality hold → release.** A lot on quality hold cannot be released to production or shipment until the required disposition and sign-off exist. Pain: holds released informally, evidence reconstructed for audits.
3. **Quote margin floor & discount authority.** A quote below the margin floor, or a discount above a limit, cannot be issued without the right authorization. Pain: margin leakage, unauthorized discounting.

The rest of this outline uses candidate **#1 (PO approval/issuance)** as the worked example; the structure transfers to any of them.

## The proof cell, defined

**Operational path (the slice):** create → approve → issue a purchase order, for one plant / category / spend band.

**Required inputs (from the customer):**
- Read access to the relevant records for that path (POs, approvers, spend limits) from the system(s) of record and any side-processes (the approval spreadsheet, the email chain).
- The *actual* approval rules as they're really applied (the authority matrix — often different from the documented one; surfacing that gap is part of the value).
- A few hours from 1–2 SMEs who know how the path really runs.

**Roles involved:**
- **Customer:** a process owner (VP Ops / controller / purchasing lead) as decision authority; 1–2 SMEs for validation; IT for read access.
- **Mimir Labs:** diagnostic + workshop facilitation; canonical-definition capture; proof-cell configuration.

**What we do (sequence):**
1. **Diagnose** the path with the reliability diagnostic: where do the system, the spreadsheet, and the report disagree about a PO's state, amount, or approval?
2. **Agree the definitions** for that path (what "approved," "issued," "over threshold," and "authorized approver" actually mean) — the canonical dictionary for this slice only.
3. **Configure the governed path:** the approval authority becomes an enforced, signed policy; the state change (issue) cannot occur unless the policy is satisfied, checked before the record changes.
4. **Run it** on real (or realistic) transactions and generate the audit trail from the path itself.

**Expected outputs (to the customer):**
- A before/after reliability picture for the path.
- The agreed definitions for the slice (a reusable asset).
- The one path running with governed state changes + policy enforcement + an audit trail generated automatically.
- A short readout mapping each result to a business consequence (fewer reconciliations, clean audit evidence, blocked-before-commit control violations).

**Success criteria (agree these up front):**
- Every issuance in the cell either satisfied the authority policy or was blocked *before* it changed the record — with a deterministic, human-readable reason.
- The audit evidence for the cell was generated by the path, not reconstructed.
- The system, the side-process, and the report agreed on the path's records at the end.
- The customer's own SME confirms the governed path matches how the business should run.

**Failure criteria (name them honestly):**
- If the "risk signals" the diagnostic surfaced turn out to be normal system structure, not real operating risk, we say so (see the false-positive walkthrough).
- If the path can't be governed without touching systems we don't control at the write point, we scope that as an integration dependency, not a claim.

**Timeline:** target **2–4 weeks** end to end (diagnose → agree definitions → configure → run → readout), depending on data access and SME availability.

**Customer effort:** deliberately bounded — read access, a handful of SME hours, one path. No ERP replacement, no rip-and-replace, no long integration project to see the value.

## Why this is the right first proof

- It's **small enough to say yes to** and **real enough to believe.**
- It proves the whole thesis (records that tell the same truth, governed) on a slice the buyer already loses sleep over.
- It's the honest on-ramp to the platform story: once one path runs on governed truth, "what if this were the system of record?" is a question the buyer asks *themselves*.
